# Synthesis comparison report

> **Unverified estimates.** The figures in this file have not been confirmed by a recorded, reproducible synthesis run or by hardware measurement. Treat every LUT, FF, BRAM, DSP, Fmax, throughput, latency and power figure here as an unverified estimate. Run `make synth_report` with your own toolchain to get real numbers.

Intended to be generated by `make synth_report`; the figures below are unverified estimates, not a recorded run. Numbers are meant as post-synthesis, pre-place-and-route.
Vendor flows (Vivado / Quartus) usually pack tighter than the open-source flow,
so Yosys numbers may be higher than vendor results (not measured).

## Notes

* The shipped `wb_top` instances both a master and a slave wired
  point-to-point, so the numbers above represent the COMBINED footprint.
  In real integrations the master and slave are usually deployed
  separately; the split between slave and master area has not been
  measured.
* The dominant area is the slave's register file (NUM_REGS x DATA_WIDTH
  FFs) plus the master's burst counter and FSM (~80 FFs). Burst-read
  pipelining adds no FFs by itself; the regfile read mux is shared.
* The address decode path is a single magnitude comparator against
  NUM_REGS plus alignment bits — a couple of LUTs each. ERR detection
  adds nothing on the critical path.
* No BRAM is required: the regfile is implemented as discrete flip-flops
  so the values are visible on `reg_storage_o` for the user logic.
* Vivado / Quartus rows are skipped automatically when those tools are
  not on PATH; on a CI runner with WebPACK / Web Edition installed they
  are intended to be populated from a real synth_design / quartus_sh run.
